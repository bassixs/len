# Проект «Лён» — обзор и актуальный статус

Документ фиксирует фактическое состояние проекта как headless-витрины поверх WooCommerce.  
Актуально на **март 2026**.

---

## 1) Цель проекта

Фронтенд в этом репозитории должен сохранять текущий внешний вид и UX, но работать от данных WordPress/WooCommerce:

- фронт: Vite MPA + кастомная верстка;
- источник данных: WooCommerce REST API;
- точка доступа на фронте: `/api/wc`.

## 3) Что работает сейчас

### 3.1 Основные пользовательские страницы

- `catalog.html` — товары из Woo, постраничная загрузка.
- `category.html` — Woo-категория + фильтры/сортировка/цена/подкатегории.
- `product.html?woo=<id>` — карточка Woo товара + related товары.
- `new.html` — динамические новинки из Woo.
- Блок карточек на `index.html` — также заполняется через Woo.

### 3.2 Наличие товаров

Наличие теперь отражается в UI во всех ключевых местах:

- бейдж `Нет в наличии` на карточках;
- статус `В наличии` / `Нет в наличии` на странице товара;
- блокировка кнопок покупки и контроля количества для отсутствующих товаров.

### 3.3 Категории и точность счетчиков

- Категория определяется динамически:
    1. по `woo_cat` из URL (если передан),
    2. затем по slug/alias/названию.
- При неоднозначности выбирается категория с наибольшим `count`.
- Если Woo API не присылает `X-WP-Total`, фронт все равно догружает весь массив страницами по 100.
- До окончания догрузки счетчик может показываться как `N+`, после — становится точным.

## 4) API-слой (dev/prod)

### Локально

В `vite.config.js` настроен proxy: `/api/wc -> /wp-json/wc/v3`.

### Продакшен

Vite proxy нет, поэтому `/api/wc` должен проксироваться сервером (сейчас: `.htaccess` rewrite).

Текущая схема рабочая, но с точки зрения безопасности это временный вариант: правильнее вынести ключи в backend/BFF и не использовать их в URL.

## 5) Структура ключевых модулей

| Файл                                    | Назначение                                                    |
| --------------------------------------- | ------------------------------------------------------------- |
| `js/modules/woo-client.js`              | запросы к `/api/wc`, пагинация товаров/категорий              |
| `js/modules/woo-map.js`                 | маппинг Woo -> модель фронта (`price`, `categories`, `stock`) |
| `js/modules/product-model.js`           | нормализация товара (`inStock`, цена, изображение, текст)     |
| `js/modules/catalog.js`                 | список каталога, сортировка, load more                        |
| `js/modules/category-products.js`       | выбор Woo-категории, фильтры, сабкатегории, фон. догрузка     |
| `js/modules/new-arrivals.js`            | раздел новинок                                                |
| `js/modules/product-cards.js`           | карточки на главной/слайдере                                  |
| `js/modules/product.js`                 | карточка товара, related, UI наличия                          |
| `js/modules/cart.js`, `cart-service.js` | клиентская корзина (localStorage)                             |

## 6) Что сделано по данным и репозиторию

- Старые статические товарные данные сокращены до fallback-уровня.
- Удалены крупные неиспользуемые директории старых изображений каталога.
- Основная логика работы витрины переключена на Woo как source of truth.

---

## 7) Что остается сделать (приоритет)

1. Убрать ключи из rewrite и перейти на безопасный server-side BFF/proxy.
2. Перевыпустить Woo REST ключи (предыдущие использовались в отладке).
3. Завести `DEPLOY.md` с пошаговым чеклистом выкладки и smoke-тестом.
4. Продумать и реализовать полноценный checkout flow через Woo (Store API/сервер).
5. Расширить автотесты на ключевые Woo-сценарии (категории, наличие, пагинация).

## 8) Локальный запуск

```bash
npm install
cp .env.example .env.local
# заполнить WOO_ORIGIN, WOO_CONSUMER_KEY, WOO_CONSUMER_SECRET, VITE_USE_WOO=true
npm run dev
```

Сборка: `npm run build`  
Просмотр билда: `npm run preview`
